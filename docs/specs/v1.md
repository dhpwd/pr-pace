# pr-pace – v1 spec

A command-line tool that measures PR pace from git history: how many pull requests a person lands, how big they are and how often they get reverted, over time, and one PR pace figure to post. It runs against one repo or a folder of repos and produces a one-line PR pace, JSON and an interactive HTML report.

## Scope

**In v1**

- Merged pull requests on each repo's default branch, read from local git history
- Squash-merged and merge-commit PRs (GitHub and GitLab conventions)
- PR pace: size-weighted PRs per week over the last 30 days, printed as one line to post
- Five figures over time: PR count, size-weighted PRs, median PR size (context for reading the first two), lines changed and revert rate (the quality check)
- Filtering and breakdown by author, with `.mailmap` support, and PRs a coding agent opened counted for the person it names as co-author
- `pace` (the PR pace line), `scan` (JSON) and `report` (self-contained HTML)

**Out of scope for v1**

- **Commits pushed straight to the default branch.** Commit frequency is personal habit, so commit counts aren't comparable between people. A possible later option: treat each day's direct commits as one PR-equivalent, comparable only with your own history
- **Rebase-merged PRs.** "Rebase and merge" lands each branch commit separately with no PR number, so local history can't group them. A later `--source github` option would read PRs from the GitHub API instead. That option would also handle organisation-wide runs without cloning, but it needs a token, works only with GitHub and can't apply the file exclusions in [Lines changed](#lines-changed)
- Bitbucket and other hosts' merge conventions

## Design decisions

These define what the numbers mean, so they're recorded here with the reason.

- **PRs, not commits, are the unit of build work.** A PR is the reviewed, landed unit in most teams' build workflow. Repos with no PRs (a notes vault, a dotfiles repo) drop out, so the tool needs no rule for which repos hold code
- **First-parent history only.** `git log --first-parent <default branch>` gives one commit per landed PR under both squash and merge-commit flows, so the two are counted the same way. Commits on PR branches are never counted individually
- **A PR whose git author is a bot counts for the first person its `Co-authored-by:` trailers name.** That covers coding agents (Copilot's coding agent, Codex's, Devin, Cursor's cloud agents) and any other GitHub App. The person named drove or finished the work, and agent identities are often shared across a team, so mapping one to a person by hand would credit every teammate's agent PRs to whoever added the mapping. A dependency or automation bot's PR (dependabot, renovate, github-actions) names a person when they pushed a commit to it, and then counts for them, as a merge-commit PR counts for whoever wrote its branch tip. Lockfiles are excluded from lines, so such PRs carry little weight. An AI tool's own trailer (Claude Code, Codex, Copilot's review suggestions) names no person and is skipped, so it can't take the credit from the person named after it. A bot PR that names no person keeps the bot as its author. The rule and its limits are in [Detecting PRs](#detecting-prs)
- **Lines changed = added + removed.** This matches the "changes" figure GitHub shows on a PR, so anyone can check it. Net growth (added − removed) would penalise refactoring and deleting dead code. Renames are detected, so moving a file doesn't count as deleting and re-adding it
- **Docs, lockfiles and generated files are excluded from lines by default.** Agents produce markdown quickly and at length, and nobody writes lockfiles or build output by hand. Tests and config count. A docs-only PR still counts as a PR, with zero lines
- **Size-weighted PRs: each PR counts √(lines ÷ 100), summed.** Each PR counts by its size, and a PR four times as big counts twice as much: a 100-line PR counts 1, a 400-line PR 2 and a 25-line PR 0.5. The 100-line reference is a fixed convention, never derived from the data, so figures compare between people and over time. Why √: for a weighting of lᵅ, splitting a change into n PRs multiplies its total by n^(1−α) and padding a PR k-fold multiplies it by k^α, and α = ½ makes the larger of the two exponents as small as possible. Splitting does count for more: landed as 4 PRs, the same 1,000 lines count 2× what they do as 1 PR. A docs-only PR has no lines, so it counts zero
- **Median PR size shows whether PRs changed size.** That is what makes PRs and size-weighted PRs diverge. It's the median because PR sizes are heavily skewed. It covers the same PRs as PR count: revert PRs are left out, and reverted PRs and docs-only PRs (0 lines) are in. Docs-only PRs pull the median down, which is correct, since they are part of why PRs and size-weighted PRs diverge. It's context for reading the other two, not a target
- **Revert rate as the quality check.** Volume can rise while quality falls. The share of PRs later reverted is cheap to detect and needs no setup
- **PR pace: size-weighted PRs per week over the last 30 days, posted as one line.** Σ √(lines ÷ 100) over PRs merged in the 30 calendar days to the run day, excluding revert PRs and PRs since reverted, × 7 ÷ 30. It measures delivered change, code that landed and stayed, not human effort. The mechanics are in [PR pace](#pr-pace)
  - **Why √.** The only public figures that bear on how work grows with PR size are Graphite's merge times for 10- to 2,000-line PRs (<https://graphite.com/blog/the-ideal-pr-is-50-lines-long>): a 2,000-line PR merges at about 12 lines an hour and a 10-line PR at 0.25–2 lines an hour, which puts merge time at lines to a power of roughly 0.26–0.66. They measure review latency, not work, so the range is a loose anchor rather than a measurement. √ (a power of 0.5) sits inside it. A log weighting would suit a figure of human effort, not delivered change, and would fall as agents improve
  - **30 days, as a rate per calendar week.** The figure is for AI-assisted building, where how people work changes month to month, so a 90-day window lags too far. The people likely to post it merge 10 or more PRs a week, which keeps 30 days reasonably stable: count noise alone is roughly ±15–20%, and the size weighting adds some. "Last 30 days" is a window people read without thinking. It's the report's "30 days" preset, so the line and the preset cover the same days
  - **Reverted PRs count zero**, like revert PRs: a reverted PR delivered nothing that stayed
  - **The share line is the only form for posting**, so the window, PR count, median PR size and version go with the figure: `PR pace 69.1/wk · 30 days to 2026-10-19 · 100 PRs · median 500 lines · pr-pace v1`. Its PR count and median cover the PRs the figure counts, so they leave out reverted PRs, where the report's PRs and median PR size tiles include them
  - **Lines always use the default exclusions.** `pace` refuses `--include-docs`, so every posted line counts lines the same way. `--exclude` stays, for generated code the default rules miss, and can only lower the figure
  - **The line carries the package's major version.** A change to the figure's definition (weighting, window, which PRs count, line exclusions) is a major version, so lines computed differently never carry the same version
  - **Known limits:**
    - A stack needing k× the lines for the same change scores about √k higher (1.6× at k = 2.5), so comparisons across stacks are weak
    - Tiny PRs are under-credited relative to their overhead: a 1-line PR counts a tenth of a 100-line one
    - A few large PRs carry much of the figure. With typical PR-size spread, the largest 5% carry roughly a fifth to a third of a √-weighted total, so one 2,000-line PR (4.5 weighted PRs) moves a 10-PR-a-week person's 30-day figure by about 5–10%, more for someone whose PRs are small
    - The figure is noisy below about five PRs a week: 30 days then holds 20 PRs or fewer, and count noise alone is ±20% or more
    - A week off takes about a quarter off
    - Only merged PRs on the default branch count, across whichever repos were scanned. Commits pushed straight to the default branch and repos left out of the scan are invisible, and the line doesn't say how many repos it covers
    - Reverts count as known at run time, so re-running later can lower a figure, and a posted line is as of its date. A PR re-landed by reverting its revert scores zero twice: the original stays reverted, and the re-land is a revert PR. Re-land as a fresh PR to be credited
    - Comparing people is weak. The strong use is one person against their own history

## Commands

The binary is `pr-pace`, runnable with `npx pr-pace` (or `npx .` from a checkout). Every command has full `--help` text, and `pr-pace --version` prints the version. Errors go to stderr, exit with status 1 and say what went wrong and what to do instead (e.g. "couldn't write out.json – check the folder exists"). Running with no command prints the help to stderr and exits with status 1. Repo warnings go to stderr as `pr-pace: warning: <repo>: <message>`, so stdout stays clean, and are kept in the repo's `warnings` in the JSON.

### `pr-pace pace [path...]`

Runs a scan and prints the PR pace line alone to stdout, exit 0. It takes `scan`'s options except `--out` and those refused below, and `--help` lists only the ones it takes. A refused option is an error saying why, not an unknown option.

| Option                              | Default | Effect                                                                                                                                                                                                                                                                                                       |
| ----------------------------------- | ------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `--from <scan.json>`                | –       | Print the line from a saved scan instead of scanning, with its `generated_at` as the run day. Paths and scan options with it are an error, as `report --from` treats them, and so is a scan whose `options.since` or `options.until` is set or whose `options.all_authors` or `options.include_docs` is true |
| `--author <email\|name>`            | as scan | Repeatable, for one person's several identities                                                                                                                                                                                                                                                              |
| `--since <date>` / `--until <date>` | –       | Refused: the line always covers the 30 days to today                                                                                                                                                                                                                                                         |
| `--all-authors`                     | –       | Refused: PR pace is one person's figure                                                                                                                                                                                                                                                                      |
| `--include-docs`                    | –       | Refused: every line counts lines the same way                                                                                                                                                                                                                                                                |

`--depth`, `--fetch`, `--branch` and `--exclude` work as in `scan`.

### `pr-pace scan [path...]`

Writes the scan result as JSON to stdout, or to `--out <file>`.

| Option                              | Default                            | Effect                                                                                                                                                                                                  |
| ----------------------------------- | ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `path...`                           | `.`                                | Each path is a repo, or a folder whose subfolders are repos                                                                                                                                             |
| `--depth <n>`                       | `1`                                | How many folder levels below a path to look for repos                                                                                                                                                   |
| `--fetch`                           | off                                | Run `git fetch --all` in each repo first, so `origin/*` and a `--branch` on any remote are current                                                                                                      |
| `--branch <name>`                   | detected                           | Override the default branch for every repo                                                                                                                                                              |
| `--author <email\|name>`            | the repo's `git config user.email` | Count only this author (exact match, ignoring case, after `.mailmap`). Repeatable. Any `--author` replaces the default, so pass one for each of your identities. Can't be combined with `--all-authors` |
| `--all-authors`                     | off                                | Count every author (for team breakdowns)                                                                                                                                                                |
| `--since <date>` / `--until <date>` | all history                        | Limit by merge date. Each takes `YYYY-MM-DD` (in the scan's timezone) or a full ISO 8601 timestamp with an offset or `Z`. A bare `--until` date includes that whole day                                 |
| `--include-docs`                    | off                                | Count docs files in lines changed                                                                                                                                                                       |
| `--exclude <glob>`                  | none                               | Extra paths to leave out of lines changed. Repeatable                                                                                                                                                   |
| `--out <file>`                      | stdout                             | Write JSON to a file                                                                                                                                                                                    |

A `--since` or `--until` value in any other form is an error naming the accepted formats, as is a `--since` later than `--until`.

### `pr-pace report [path...]`

Runs a scan with the same options and writes the HTML report.

| Option               | Default        | Effect                                                                                              |
| -------------------- | -------------- | --------------------------------------------------------------------------------------------------- |
| `--from <scan.json>` | –              | Build the report from a saved scan instead of scanning. Paths and scan options with it are an error |
| `--out <file>`       | `pr-pace.html` | Where to write the report                                                                           |
| `--open`             | off            | Open the report in the default browser                                                              |

## Behaviour

### Finding repos

- A path containing `.git` (directory or file) is a repo. Otherwise, search its subfolders down to `--depth`. A repo's own subfolders aren't searched
- Skip `node_modules` and dot-folders when searching
- A path that isn't a folder, or one whose search finds no repos, is an error naming that path
- A repo's `name` is its folder name. Where scanned repos share a folder name, each takes as many parent folders as it needs to be told apart (`work/x/app`, `oss/x/app`)
- If the same commit SHA appears in two scanned repos (e.g. two clones), count it once: the first repo in scan order keeps it, and the later repo gets a warning saying how many PRs were already counted under which repo. Where only the later repo holds the revert of a kept PR, the kept PR still takes its `reverted_by`

### Default branch

In order: the target of `refs/remotes/origin/HEAD`, then `origin/main`, then `origin/master`, then local `main`, then local `master`. Remote-tracking branches come first so the result reflects what has landed rather than local work. A repo with none of these is reported as a warning and skipped (it stays in `repos` with `branch: null`). `--branch` names a ref used as given in every repo, and a repo without it is skipped with a warning. A repo git can't read at all (a worktree whose main repo was deleted, an empty `.git` folder, a repo git refuses as dubiously owned) is skipped with git's own error rather than a `--branch` hint.

### Detecting PRs

Walk the default branch with `--first-parent`. For each commit:

| Pattern                                                                                                                  | Method   | PR number | Author                                                                                                    | Diff                                                      |
| ------------------------------------------------------------------------------------------------------------------------ | -------- | --------- | --------------------------------------------------------------------------------------------------------- | --------------------------------------------------------- |
| Two or more parents, subject `Merge pull request #N from …` (GitHub) or body containing `See merge request …!N` (GitLab) | `merge`  | N         | Author of the second parent (the branch tip), or when that's an agent, the person the tip's trailers name | First parent → merge commit                               |
| Two or more parents, subject ending `(#N)` (GitHub's "Pull request title" merge-commit message setting)                  | `merge`  | N         | Author of the second parent (the branch tip), or when that's an agent, the person the tip's trailers name | First parent → merge commit                               |
| One parent, subject ending `(#N)`                                                                                        | `squash` | N         | Commit author, or when that's an agent, the person the commit's trailers name                             | Parent → commit                                           |
| Anything else                                                                                                            | –        | –         | –                                                                                                         | Not counted. Tallied per repo as `direct_commits_ignored` |

- The subject is the message's first paragraph, as git defines it
- `title` is the subject with any trailing `(#N)` suffix stripped. For a `Merge pull request #N from …` commit, `title` is the first non-empty line of the commit body (GitHub puts the PR title there), falling back to the subject when the body is empty. A GitLab merge keeps its subject as the title
- Merge time is the commit's committer date
- Author identities go through `.mailmap` (use `%aN` / `%aE`)
- An identity is an agent if its email, after `.mailmap` and ignoring case, matches `^\d+\+[^@]*\[bot\]@users\.noreply\.github\.com$` (any GitHub App bot's no-reply address) or is one of the agent addresses that pattern misses: `198982749+Copilot@users.noreply.github.com` (Copilot's coding agent, as squash and commit author), `242516109+Codex@users.noreply.github.com` (Codex's coding agent, shown as `openai-code-agent[bot]`, as squash and commit author), `cursoragent@cursor.com` and `cursor-agent@cursor.com` (Cursor's cloud agents, as commit author). GitHub's squash commit takes the PR opener as author, so a PR an agent opened is authored by the agent
- A PR whose author is an agent counts for the first `Co-authored-by:` trailer whose identity, after `.mailmap`, is neither an agent nor an AI tool. For a squash PR that's in the squash commit's message, and for a merge PR in the branch tip's. The PR takes that identity's mapped name and email as `author_name` and `author_email`, and keeps the agent's email in `agent_email`. Only the first person counts, so `--all-authors` counts each PR once. A PR with no such trailer keeps the agent as its author, and a PR whose author isn't an agent keeps its author whoever its trailers name
- A trailer identity is an AI tool if its email, after `.mailmap` and ignoring case, matches `^no-?reply@` (a `noreply` or `no-reply` local part at any domain, such as Claude Code's `noreply@anthropic.com`, Codex's `noreply@openai.com` and OpenCode's `noreply@opencode.ai`) or `^\d+\+copilot@users\.noreply\.github\.com$` (GitHub's Copilot accounts: `175728472+Copilot@users.noreply.github.com` on committed Copilot review suggestions and Autofix fixes, and `223556219+Copilot@users.noreply.github.com`, named "Copilot" or "Copilot App"), or is one of `codex@openai.com` (Codex), `267193182+codex@users.noreply.github.com` and `codex@users.noreply.github.com` (the no-reply address of Codex's GitHub account `codex`, with and without its id), `openhands@all-hands.dev` (OpenHands), `amp@ampcode.com` (Amp), `copilot@github.com` (GitHub Copilot) and `jules@google.com` (Google Jules). A person's GitHub no-reply address has their login in its local part, so the first pattern doesn't match it. These are the tools' own trailers on commits made with them, and a squash body carries every branch commit's trailers ahead of GitHub's closing block, so one can come before the person's. AI tools are skipped only when picking the trailer
- Trailers are read from any line of the message, not only its final trailer block, since GitHub can place them elsewhere in a squash body. Each is `Name <email>`, matched ignoring case (`Co-authored-by` and `Co-Authored-By` both occur), CRLF line endings and surrounding whitespace, and counts only with a name and a non-empty email
- A repo's trailer identities from its in-range agent PRs go through `.mailmap` in one `git check-mailmap --stdin` call, deduplicated, each passed as `Name <email>` so the mapped name comes back too. The call runs only when some agent PR has a trailer. If it fails, the trailers count as written, with no warning
- Crediting runs after the branch tips' authors are read and before the author filter, so the filter, the no-match warning and the JSON all see the credited person
- The default author filter matches the email from `git config user.email` as seen from each repo, so per-repo config is respected. That email, and each email-shaped `--author` value, goes through the repo's `.mailmap` (`git check-mailmap`) so the filter matches the mapped identities. A `--author` value in the form `Name <email>`, with or without the `(count)` the no-match warning below adds, matches by its email. A value without `@` matches the mapped author name
- A repo with no `user.email` configured counts no PRs under the default filter and gets a warning to pass `--author`, once for each of your identities, or `--all-authors`
- If a repo has PRs in the date range but none match the author filter, add a warning to that repo naming the five most frequent PR authors found (`Name <email> (count)`), with a hint to pass `--author`, once for each of your identities. This catches a local git email that differs from the one GitHub records on squash merges, or from the one a coding agent names as co-author. A coding agent among the listed authors gets a further hint (see [Repo warnings](#repo-warnings))
- If PRs in the date range count for a person's GitHub no-reply address (an agent identity, by the rule above, is never one) that the author filter doesn't match, read `origin`'s URL with one `git remote get-url origin` call, and warn about each such address that belongs to the repo's owner. That's the address Copilot, Codex's coding agent and Cursor name you by, and the one GitHub records your own squash merges under when email privacy is on. Local git can't tell a teammate's no-reply address from yours, but in a repo under your own GitHub account the owner's login is yours. In detail:
  - A no-reply address is an email that, lowercased, matches `^(?:\d+\+)?([^@]+)@users\.noreply\.github\.com$`: the `<id>+<login>@` form or the older `<login>@` form, with the login captured. It's checked against the identity each PR counts for, after the branch tip's author and co-author crediting, whether or not an agent opened the PR
  - The owner comes from a `github.com` URL (host compared ignoring case) in one of the forms `https://[<user>@]github.com/<owner>/<repo>[.git]` (any user part without `/` or `@`, such as `x-access-token:<token>`), `git@github.com:<owner>/<repo>[.git]` and `ssh://git@github.com[:<port>]/<owner>/<repo>[.git]`, each with an optional trailing `/` (`git clone` keeps one given in the URL). An address belongs to the owner when its login equals the owner, ignoring case
  - The warning fires whether or not the no-match warning does, under `--author` as well as the default filter, and in a repo with no `user.email` alongside that warning. Never under `--all-authors`, where every PR matches
  - No `origin`, a failed `git remote get-url`, another host or a URL in another form gives no owner-match warning and no other warning about it
  - The owner is taken to be you, so in a clone of someone else's personal repo the warning names their address when their PRs miss your filter. That's why it says "if it's you"

**Known limits of crediting agent PRs:**

- An agent PR with no `Co-authored-by:` naming a person stays credited to the agent. Jules adds none by default
- An agent identity outside the pattern and the address list counts as a person, so an unlisted agent account that opens a PR keeps the credit. An AI tool identity outside the trailer rule also counts as a person and, as a trailer before the person's in an agent PR's message, takes the credit from them. Any AI tool, listed or not, that authors a squash commit or a merge PR's branch tip counts as a person and takes the credit
- A person whose trailer email has a `noreply` or `no-reply` local part is skipped as an AI tool, so their agent PR goes to the next person named or stays with the agent, unless a `.mailmap` line maps that address to another one (mapping runs before the check)
- A merge PR is credited from its branch tip's trailers only, so an agent branch whose last commit names no one (a merge from the default branch, a fix-up) stays with the agent even when earlier commits name the person
- A backport or cherry-pick bot's PR keeps the original commits' author, so GitHub's squash names that person and the backport counts for them as well as the original PR, as a merge-commit backport already does
- The trailer names the person by the address the agent chose (Copilot, Codex's coding agent and Cursor a `users.noreply.github.com` address, Devin the real email), which may differ from your git email. The PR then needs `--author` or a `.mailmap` line to count as yours, as a squash merge recorded under another email does. When that address is your GitHub no-reply address and the repo is under your own GitHub account, a warning names it while it misses the filter (see [Repo warnings](#repo-warnings)). Elsewhere nothing warns unless none of the repo's PRs match, when the no-match warning lists the most frequent PR authors. A remote under an SSH host alias (`git@github-personal:<owner>/<repo>`) or `ssh.github.com` isn't recognised, so those repos get no owner-match warning
- A bot PR that a teammate pushed a commit to can name the teammate first, depending on the repo's squash message setting, and then counts for them

### Lines changed

Per PR, from `git diff --numstat -M` over the diff in the table above:

- Binary files (numstat `-`) are ignored
- Excluded by default:
  - docs: `*.md`, `*.mdx`, `*.markdown`, `*.rst`, `*.adoc`, `*.txt` (extensions matched ignoring case). A `.txt` file still counts when it is config: a name containing `requirements` or `constraints`, any `.txt` under a `requirements/` folder at any depth, `CMakeLists.txt` and `robots.txt` (matched ignoring case). Build output, linguist attributes and `--exclude` globs still exclude them
  - lockfiles: `package-lock.json`, `yarn.lock`, `pnpm-lock.yaml`, `bun.lock`, `bun.lockb`, `Cargo.lock`, `poetry.lock`, `uv.lock`, `Gemfile.lock`, `composer.lock`, `go.sum`
  - build output: `*.min.js`, `*.min.css`, `*.map`, and anything under a `dist/`, `build/`, `vendor/` or `node_modules/` folder at any depth
  - anything the repo's `.gitattributes` marks `linguist-generated`, `linguist-vendored` or `linguist-documentation` (set or `=true`), read from the default branch's tip with `git check-attr --stdin --source=<branch>` in one batch per repo. `--source` needs git 2.40 or later. Without it the repo gets a warning and the linguist exclusions are skipped
- `--include-docs` drops the docs extension list only. Files marked `linguist-documentation` stay excluded
- `--exclude` adds globs: `*` matches within a folder, `**` across folders, `?` one character, everything else is literal. As in `.gitignore`, a glob without `/` matches a file or folder name at any depth (`*.snap`, `fixtures`), a leading or inner `/` anchors it at the repo root, where it matches a path or any folder above it (`/api`, `src/gen`, `src/**/*.gen.ts`), and a trailing `/` alone doesn't anchor (`build/` matches at any depth)
- `lines = added + removed` over the files kept. Lines in excluded files are reported separately as `excluded_lines`
- `weighted_prs = √(lines ÷ 100)`, rounded to three decimals. The report computes it again from `lines` and sums the unrounded values, rounding only for display (two decimals): per-PR values mostly fall between 0.1 and 5, so rounding each before summing would lose noticeable precision

### Reverts

- A PR is a revert if its title starts `Revert "`, or its message contains `This reverts commit <sha>` where `<sha>` (full or a prefix of at least seven characters) is an earlier PR commit in the repo's first-parent history. A `This reverts commit` line naming any other SHA is ignored: a squash PR's body carries every branch commit's message, so a branch commit that reverted another branch commit would otherwise make an ordinary PR count as a revert
- Link a revert to the original PR by the first such SHA. Otherwise, take the quoted text from `Revert "…"` in the title, strip any `(#N)` suffix and match it against an earlier PR's raw subject or its title (each with any `(#N)` suffix stripped), taking the most recent match. A revert with no match still counts as a revert, unlinked
- Detection and linking run over the full first-parent history, before the author filter and before `--since`/`--until`. So another author's revert still marks your PR, a PR in range reverted after `--until` keeps its `reverted_by` and a revert whose original predates `--since` still counts as a revert
- A direct commit (not a PR) whose message contains `This reverts commit <sha>` naming an earlier PR commit also marks that PR as reverted. This is how `git revert` pushed straight to the default branch shows up. The direct commit is linked by SHA only, never by its title, and stays uncounted like any direct commit
- Revert PRs are left out of PR count, size-weighted PRs, median PR size and lines. Reverting isn't progress
- The original PR is marked `reverted_by` (the first revert's SHA, whether a revert PR's or a direct commit's – PR numbers aren't unique across repos) and counts towards the revert rate of the period it was merged in
- Recent periods will understate the revert rate because their PRs have had less time to be reverted. The report says so beside the metric

### Repo warnings

A repo's warnings say what happened and what to do. Besides those above (no default branch, `--branch` not found, a repo git can't read, no `user.email`, no PRs matching the author filter, PRs crediting the owner's no-reply address that the filter misses, PRs already counted under another repo, linguist attributes unreadable), a failed `git fetch` scans the local copy as it is and a failed `git log` skips the repo. That includes a log too large for Node to hold as one string (about 512M characters). An unreadable set of merge PRs' branch commits falls back to the merge commits' authors, and with no tip message to read, those PRs aren't credited to a co-author. A skipped repo carries only the reason it was skipped.

When the no-match warning lists a coding agent, it ends with a hint naming each one as `Name <email>`, after the existing text:

```
no PRs match the author filter. Most frequent PR authors: … – pass --author to choose, once for each of your identities. Copilot <198982749+Copilot@users.noreply.github.com> is a coding agent with no co-author naming a person on these PRs – if only you use it, pass its email as an extra --author alongside your own or map it to yourself in .mailmap, otherwise turn on the agent's setting that adds you as co-author
```

With two or more ("A and B", "A, B and C"): `… are coding agents with no co-author naming a person on these PRs – if only you use them, pass their emails as extra --author values alongside your own or map them to yourself in .mailmap, otherwise turn on each agent's setting that adds you as co-author`. The coding agents are the four agent addresses in [Detecting PRs](#detecting-prs) and the GitHub no-reply logins (the part between `+` and `@`) `copilot-swe-agent[bot]`, `devin-ai-integration[bot]`, `cursor[bot]` and `google-labs-jules[bot]`. Dependency and automation bots such as `dependabot[bot]` get no hint, since mapping one to yourself would count its dependency bumps in your PR pace.

The owner-match warning comes after the no-match warning, one for each of the owner's no-reply addresses, grouped by lowercased email and labelled `Name <email>` from the first PR seen, most PRs first and then by label:

```
3 PRs credit dev-one <1001+dev-one@users.noreply.github.com>, the GitHub no-reply address of this repo's owner, which the author filter doesn't match – if it's you, pass it as an extra --author alongside your own email, or map it to your usual identity in .mailmap
```

With one PR it starts `1 PR credits …`.

### Periods

- Bucket by merge time in the scan's timezone (`options.timezone`), in the CLI and in the report alike, so every reader of a report sees the same buckets whatever their own zone
- Weeks start on Monday (ISO weeks)

### PR pace

- PR pace is computed from a scan result, so `pace` and `pace --from` give the same line for the same scan. The run day is the day `generated_at` falls on in `options.timezone`. The window runs from the start of the day 29 days before the run day to the start of the day after it, so it holds 30 calendar days and the run day is partial
- It counts the PRs merged in the window with `is_revert` false and `reverted_by` null, across every scanned repo after the same-commit dedupe. A docs-only PR (0 lines) counts in the PR count and median and adds nothing to the pace
- The pace is Σ √(lines ÷ 100) over those PRs, summed from `lines` rather than the rounded `weighted_prs`, × 7 ÷ 30. The line shows it with `toFixed(1)`, which rounds the binary float, so a value on a .x5 boundary can round down. The median PR size is rounded half up to whole lines, as in the report's tile (208.5 shows as 209). Numbers have no thousands separators, and "PR" and "line" are singular for 1
- The version is the package's major version (`v0` before 1.0.0)
- With no PRs in the window the line still prints: `PR pace 0.0/wk · 30 days to 2026-10-19 · 0 PRs · median – · pr-pace v1`
- Every line matches `^PR pace \d+\.\d/wk · 30 days to \d{4}-\d{2}-\d{2} · \d+ PRs? · median (\d+ lines?|–) · pr-pace v\d+$`
- The live `pace` runs the same unbounded scan as `scan`, so its line matches `pace --from` on a saved `scan` of the same repos. Reverts count as known when the scan runs, as revert linking always covers full history (see [Reverts](#reverts))

- `options.timezone` is the scanning machine's IANA zone (`Intl.DateTimeFormat().resolvedOptions().timeZone`). `generated_at` and `merged_at` carry that zone's offset, to the second
- `options.authors` lists the `--author` values as given. Without `--author` or `--all-authors`, it lists the distinct default emails used (each repo's `git config user.email` after `.mailmap`). It's an empty list when `all_authors` is true, and the report offers split-by-author only then
- `options.exclude` lists the `--exclude` globs as given, or `[]`
- `options.since` and `options.until` hold the values as given, or `null`
- `repos[].prs` counts the PRs that pass the author and date filters – the same set as that repo's rows in `prs`, revert PRs included
- `repos[].direct_commits_ignored` counts the first-parent commits that aren't PRs, under the same author and date filters
- `prs` holds every PR that passes the filters, revert PRs included (`is_revert: true`), so a reader can trace them. `added` and `removed` cover the files kept. Rows are sorted by `merged_at`
- `author_name` and `author_email` are who the PR counts for. `agent_email` is the agent's email, after `.mailmap`, when the PR's git author is an agent ([Detecting PRs](#detecting-prs)), whether or not a person took the credit, and otherwise `null`. The report and `pace` don't read it, so a saved scan without it still loads

## HTML report

The report is one self-contained file. It embeds the scan JSON, leaving out each repo's `path` and `warnings`: the report shows neither, and both can carry local folder names into a file that gets sent around. It makes no external requests (its tab icon is a `data:` URI) and draws its charts as inline SVG with vanilla JS, so it works offline and when attached to a message.

**Controls**

- Date range: presets (last 30 days, 90 days, 12 months, all) plus custom from/to. Presets count back from `generated_at`, not from when the page is opened, so an attached report shows the same numbers whenever it's read. Like the periods, they work in days in `options.timezone`: 30 and 90 days end on `generated_at`'s day and include it, and 12 months runs from the day after the same date a year earlier. "All" runs from `--since` (or the earliest PR) to `--until` (or `generated_at`'s day). A remembered custom range that holds none of this report's days falls back to 12 months
- Period: day, week, month
- Metric: PRs, size-weighted PRs, median PR size, lines changed, revert rate, defaulting to PRs. Size-weighted PRs are labelled "Weighted PRs" in the control, summary row, PR list and chart title
- Split: none, by repo, by author (author only when the scan used `--all-authors`)
- Repo filter: checkbox per repo, with all/none

**Display**

- A header line giving when the scan ran, how many repos it covered, the authors counted, the timezone and what lines changed leave out, naming any `--exclude` globs in quotes. With no authors to count, it says whether no repo could be scanned or no scanned repo had `user.email` set
- Summary row for the selected range: PRs, size-weighted PRs, median PR size, lines, revert rate, each with the change against the previous range of equal length. "All" has no previous range, so it shows no change figures, and nor does a range whose previous range starts before `--since`. The revert-rate tile always carries the note that recent PRs have had less time to be reverted
- The median PR size tile is the median of all PRs in the range, not an average of the period medians. Its change is a percentage, like lines changed (absolute lines when the previous median is 0), and isn't coloured good or bad, since the figure is context, not a target. A range with no PRs has no median: the tile shows "–", and there's no change figure when either range has no PRs
- Size-weighted PRs show two decimals in the tile, tooltip, list summary, PR list rows and moving average. Median PR size shows whole lines, rounded half up (an even count can give 208.5, shown as 209). Axis ticks use a compact form and never repeat a label
- Bar chart of the selected metric per period, stacked when split, with a 4-period moving average line over the total. Revert rate and median PR size with a split draw side-by-side bars per series: rates don't stack, and series medians don't add up to the period's median. Revert rate's moving average pools the four periods (reverted ÷ PRs across them). Median PR size's, labelled "4-period median", is the median of all PRs across the four periods, not an average of period medians, because a period with one or two PRs swings a median a lot. A period or series with no PRs has no median and draws no bar (a gap, not 0)
- Series colours follow the entity, not the filter: up to eight repos or authors get a hue each, ranked by PR count over the whole scan. Past eight, the top seven do and the rest share "Other"
- Tooltip on hover or keyboard focus with the period's values per series
- Clicking a bar lists that period's counted PRs (merge date, repo, number, title, author when split by author is available, lines, weighted PRs) so any number can be traced to its PRs. Reverted PRs are marked. For PRs, size-weighted PRs and lines the listed rows sum to the bar within display rounding. For median PR size, the median of the listed rows' lines equals the bar, and the summary gives the PR count and median ("12 PRs · median 208 lines"). For revert rate, reverted ÷ listed equals the bar. Under a split, the list covers every series in the period, and for revert rate and median PR size its summary gives each series' reverted ÷ PRs or median, matching that series' bar. Revert PRs merged in the period are noted, not listed. Selecting a bar by keyboard keeps focus on it
- Light and dark themes following the system setting
- Usable at phone width

Selected controls are remembered in `localStorage` for each set of scanned repo names, with the page working normally if storage is unavailable. Reports opened from disk share one storage origin, so a report on the same repo names picks up the controls and one on other repos starts from the defaults.

## Implementation constraints

- Node 22 or later, ES modules, no runtime dependencies (`node:child_process`, `node:fs` and `parseArgs` from `node:util`). Nothing newer than Node 22.0 is in use. From 1.0.0, raising the floor is a major version, which changes the version on every posted PR pace line, so the floor stays at 22 past its end of life. `npm run typecheck` (`tsc --noEmit` with `checkJs`, `strict` and `@types/node` 22.x) catches most APIs newer than Node 22.0, but not all: `@types/node` 22.x follows the newest 22 release, so it has APIs added after 22.0 (`path.matchesGlob` arrived in 22.5.0). `--exclude` globs go through a hand-written matcher (`globToRegExp` in `src/exclude.js`) rather than `path.matchesGlob`, for two reasons:
  - `path.matchesGlob` doesn't exist in Node 22.0–22.4. From 22.5.0 until 22.17.0 it prints an `ExperimentalWarning` to stderr, and it is documented as experimental until 22.20.0
  - Its syntax isn't the one [Lines changed](#lines-changed) defines for `--exclude`. It's minimatch, where `*` skips dotfiles, `[...]` and `{a,b}` are glob syntax rather than literal, and on macOS and Windows any file or folder name in the glob that contains a wildcard matches ignoring case (`*.SNAP` matches `a.snap`, while `src/Gen` doesn't match `src/gen`). Using it would change which lines are excluded, and differently per OS
- Per-commit work is one `git log` call per repo for commits and numstat (`--first-parent --diff-merges=first-parent --numstat -M`), plus one batched call for second-parent authors and messages, one `git check-attr --stdin` and one batched `git check-mailmap` for co-author identities. A fixed number of setup calls per repo sits outside that budget: `git config user.email`, default-branch resolution, `git check-mailmap` for the author filter, `git remote get-url origin` (run only when a PR credits a person's no-reply address the filter misses) and `git fetch` under `--fetch`. Never a process per commit or PR
- Read-only against scanned repos, apart from `--fetch`
- Each scanned repo is found from its own folder. Git runs without the variables that tie it to one repo (`git rev-parse --local-env-vars` less its config variables, so config set through the environment still applies), and with `GIT_CEILING_DIRECTORIES` at the repo's parent, so a broken `.git` folder inside another repo fails rather than reading the outer repo. The technique and why: `docs/patterns/git.md`
- The report's browser code is inlined from `src/time.js` and `src/report/client.js` with `Function.prototype.toString`, so every export of those modules is a function declaration that uses only browser globals, its own locals and other inlined exports. The technique and its pitfalls: `docs/patterns/report-inlining.md`
- `src/pace.js` takes `weightOf`, `medianLines` and the "30 days" preset (`presetRange`) from `src/report/client.js`, so the report and PR pace share one definition of each. A change to any of them changes PR pace lines, which is a major version
- The repo will be made public. Keep personal details, private repo names and real data out of code, tests, fixtures and docs. Fixtures are generated, never copied from real repos
